# P1 — two machines, two storages, one file

P1 is the smallest thing that proves the promise in `DECISIONS.md`: the files stay in
each party's own storage, and the hub keeps only the record. One container, one PDF
published as revision A and then B, transferred directly from one agent to the other
and hashed on arrival (B1, B2, B5).

Everything here is headless. There is no GUI, no tray icon, no file watcher and no web
page: those are later phases.

---

## 1. Run it

The venv already has FastAPI, uvicorn, httpx, cryptography and pytest. Always use its
interpreter by full path; on this Windows host the MSYS path (`/z/...`) does not work for
native programs.

```bash
cd Z:/dev/cde

# the seven tests (real processes, real HTTP, two roots)
Z:/dev/cde/.venv/Scripts/python.exe -m pytest tests -q

# the demo: hub + two agents, ~3 MB of PDFs, summary table
Z:/dev/cde/.venv/Scripts/python.exe scripts/p1_demo.py
```

`scripts/p1_demo.py --keep` leaves the work directory so you can open the PDFs and look
at `agent-b/_cindy/...` yourself. `--workdir DIR` puts it somewhere you choose.

The demo takes about fifteen seconds. It prints the summary table described in the task:
revision, container, sha256 (first 12), size, holder, transfer ms, hub bytes before and
after, and the verification result.

Each test and the demo start their own hub on a free port with a fresh SQLite file and
two fresh roots, so nothing is shared and nothing has to be cleaned up by hand.

## 2. What the seven tests prove

| Test | What it proves |
|---|---|
| **T1** `publish_and_pull_are_byte_identical` | A publishes revision A of `S100`; B pulls it over HTTP from A's blob service. B's file has the same sha256 and is byte-for-byte identical. Both parties appear as holders of the same revision. |
| **T2** `hub_stores_no_file_bytes` | The blob is over 1 MB; the hub's data directory grows by a few bytes at most while it moves. Both numbers are printed. This is the claim the product rests on. |
| **T3** `supersede_keeps_both_revisions` | Publishing revision B with `--supersedes <A>` adds a second revision. A's file is still on disk and still read-only, B holds both files, the container's current revision is B. Nothing is replaced (A3). |
| **T4** `tamper_is_detected_and_repaired` | B's local copy is corrupted in place (same size, one flipped byte). `verify` exits non-zero and reports `hash-mismatch`; `repair` re-fetches from A and the hash matches again. A peer that serves the wrong bytes is refused by the transfer itself and its temp file is deleted. |
| **T5** `wrong_key_is_rejected_and_leaves_no_row` | A revision record signed with a key that is not the author's is answered 403 by the hub and no revision row is created. |
| **T6** `link_loss_fails_cleanly_then_converges` | With the only holder's blob service stopped, `pull` fails with a non-zero exit, leaves no partial files and registers no holders. After the service is back, `pull` converges: both files arrive, there are still exactly two revisions and one holder row per party per revision. |
| **T7** `pulling_twice_duplicates_nothing` | A second `pull` transfers nothing, creates no second file and no second holder row. |

T5 is the one test that runs in-process against the FastAPI app instead of a separate
hub process, because its subject is the hub's check, not the transfer.

Measured on this machine (1.3 MB PDF per revision, both revisions pulled):

```
T2: blob 1300943 bytes transferred; hub data dir 77824 -> 77824 bytes (growth 0 bytes)
```

The growth is zero because the new holder and audit rows fit into pages SQLite had already
allocated. The whole hub data directory — schema, project, parties, container, both
revisions, holders and audit — is 77,824 bytes, about 3% of the 2.6 MB that moved, and
none of those bytes are file content. The demo also scans every file in the hub directory
and reports whether any of it is a published blob or looks like a PDF; it does not.

To see the size argument at a larger scale, raise `padding_bytes` in
`scripts/pdf_fixture.py`; nothing in the hub changes with the size of the file.

## 3. What each piece is

```
hub/          FastAPI + SQLite. Metadata only: projects, parties, containers,
              revisions (signed), holders, audit.
agent/        the `cindy` CLI, run as `python -m agent` (no install step):
              init, serve, publish, pull, verify, repair, status.
scripts/      p1_demo.py (the whole story once) and pdf_fixture.py (real PDFs > 1 MB).
tests/        the seven acceptance tests plus the harness that starts real processes.
```

On disk, one machine holds:

```
ROOT/.cindy/state.json        party id, project id, hub URL, blob port, Ed25519 key
ROOT/.cindy/index.json        sha256 -> local path. This disk's map, not the record.
ROOT/_cindy/<project>/<container number>/<code>_<file name>
```

Published copies are set read-only. `publish` never writes over an existing file: a
changed file is a new revision at a new path. `repair` is the only writer that replaces
an existing path, and it only does so with bytes that hash to the recorded sha256.

### The signed record

A revision is signed with the author's Ed25519 key over a canonical JSON encoding of
`container_id, sha256, size, media_type, file_name, revision_code, author_party,
created_at, supersedes_id`. The hub rebuilds that payload from the request and verifies
it against the public key it recorded when the invite was accepted. A mismatch is 403
before any row is written. `hub/records.py` is the single definition used by both sides,
so the two can never drift.

### The hub holds no bytes, by construction

There is no blob table, no byte column and no proxy endpoint. The hub's only knowledge of
a file is its hash, its size and who says they hold it. Transfers go from the holder's
`GET /blob/<sha256>` straight to the puller; if a party is unreachable, the pull fails
rather than routing through the hub. Relay is P5 and is not built.

## 4. The same thing on two real PCs on a LAN

The demo simulates two machines with two directories and two ports on one host. On a
LAN the only differences are addresses and Windows Firewall.

**Machine 1 — the hub (say `192.168.1.10`)**

```bash
cd Z:/dev/cde
Z:/dev/cde/.venv/Scripts/python.exe -m hub --db C:/cindy/hub.db --host 0.0.0.0 --port 8080
```

`--host 0.0.0.0` is required: the default binds only to `127.0.0.1`, which the other PC
cannot reach. The hub needs no other port open. Its SQLite file is the whole record; back
it up by copying the directory.

Create the project and the two invitations (any HTTP client; shown with curl):

```bash
curl -s -X POST http://192.168.1.10:8080/projects -H "content-type: application/json" -d '{"name":"Riverside School"}'
# -> {"id": "prj_...", ...}

curl -s -X POST http://192.168.1.10:8080/projects/prj_.../parties -H "content-type: application/json" -d '{"name":"Alpha Design"}'
curl -s -X POST http://192.168.1.10:8080/projects/prj_.../parties -H "content-type: application/json" -d '{"name":"Beta Construction"}'
# each returns an invite_token; it is shown once, so copy it now
```

Create the container once (the originator's party id is in the first invite response):

```bash
curl -s -X POST http://192.168.1.10:8080/projects/prj_.../containers -H "content-type: application/json" \
  -d '{"number":"D-101","title":"Ground floor plan","type":"drawing","originator_party":"pty_..."}'
```

**Machine 2 — Alpha Design (`192.168.1.21`)**

```bash
Z:/dev/cde/.venv/Scripts/python.exe -m agent init \
  --root C:/Projects/Riverside --hub http://192.168.1.10:8080 \
  --invite "prj_...~pty_...~..." --host 192.168.1.21 --port 45401

Z:/dev/cde/.venv/Scripts/python.exe -m agent serve --root C:/Projects/Riverside
Z:/dev/cde/.venv/Scripts/python.exe -m agent publish --root C:/Projects/Riverside \
  --container D-101 --path C:/Projects/Riverside/D-101_A.pdf --rev A
```

`--host` is the address the *other* party will connect to, so it must be the machine's LAN
address, not `127.0.0.1`. `init` announces `host:port` to the hub; that announcement is the
only thing the hub knows about where the bytes are. `serve` then binds `0.0.0.0` on that
port.

**Machine 3 — Beta Construction (`192.168.1.22`)**

```bash
Z:/dev/cde/.venv/Scripts/python.exe -m agent init \
  --root D:/CDE/Riverside --hub http://192.168.1.10:8080 \
  --invite "prj_...~pty_...~..." --host 192.168.1.22 --port 45402

Z:/dev/cde/.venv/Scripts/python.exe -m agent serve --root D:/CDE/Riverside
Z:/dev/cde/.venv/Scripts/python.exe -m agent pull --root D:/CDE/Riverside
```

**Ports to open on each machine's firewall**

| Machine | Port | Why |
|---|---|---|
| hub | 8080/tcp | agents and browser talk to the hub |
| Alpha | 45401/tcp | the other agent fetches blobs from it |
| Beta | 45402/tcp | same, in the other direction |

Use fixed ports for the agents, because the announced address has to stay valid across a
restart. If a machine's IP changes, re-announce with a fresh `init --force` or update the
address through the hub, or the other side will try the old address and fail.

To publish from the second machine, run `cindy publish` there against the same container
number; the record is shared, the bytes are not.

## 5. What the link-loss test does and does not prove

**It is simulated by stopping the holder's blob service, not by unplugging a cable.** T6
kills the process serving `GET /blob/...` on agent A, runs a pull on B and checks that it
fails cleanly, then restarts A's service and checks that the next pull converges.

That exercises the same code path a real outage does — a connection refused or timed out
between two agents — but it does **not** test a cable being pulled on the hub side, a
half-open TCP connection, an IP change, or a machine that sleeps mid-transfer. It also
does not test the hub being unreachable during a pull; the pull would fail at the first
hub request instead, and the record would be unchanged.

`pull` has no durable queue: the work to do is always "revisions in the record that I do
not hold and can verify", recomputed from the hub on every run. That is why a failed pull
loses nothing and a repeated pull converges — there is no local state to get out of step.
The demo and T6 show the consequence: fail, then succeed, with no duplicates.

## 6. Not in P1

Deliberately absent, because each is a later phase and building it now would hide whether
the core works:

- the container tree, typed attributes and delegation (P2)
- states, the two signed gates, hiding and visibility reports (P3)
- automatic replication across many holders (P4) — P1 has holders and `repair`, no policy
- relay through the hub (P5); there is no relay code and the hub cannot proxy bytes
- transmittals (P6) and handover export (P7)
- a GUI, tray icon, file watcher, web UI, and any vendor storage API
- authentication of hub API calls: anyone who can reach the hub can create a project, a
  party or a container. Revisions are signed, which is what makes the *record* trustworthy.
  Per-caller authorisation belongs with the visibility rules in P3.
- deletion of any kind (B6)

## 7. Assumptions made while building P1

These are choices the brief left open; each is small and easy to reverse.

1. **Invite flow.** `POST /projects/PID/parties` is used twice on one endpoint: with
   `{name}` it creates the party and returns the invite token; with
   `{invite_token, public_key_b64}` the device claims it and the hub records the public
   half. The token names the project and the party (`project~party~secret`) so
   `cindy init` needs no other input. Only the token's SHA-256 is stored.
2. **One extra table, `party_link`.** Holds the announced address and the invite-token
   hash. The seven tables in the brief are exactly as specified; identity data did not
   belong in `party`.
3. **Two extra read endpoints, `GET /projects/PID/containers` and the inline `holders`
   array on revisions.** Publishing by container number and printing `status` need the
   container list; the record stays the single source. No file bytes are involved in
   either.
4. **Idempotency key is `(container_id, sha256)`.** Same bytes in the same container is
   one revision forever; the same bytes in a different container is a different revision,
   because the container is the unit (A1).
5. **Container state defaults to `published`.** P1 has no state machine; `state` is a
   column that P3 will drive.
6. **Holder registration is unsigned in P1.** A party says "I hold this revision at this
   path"; the path is a claim about its own storage. Signing holder claims is cheap to add
   and belongs with the replication policy in P4.
7. **Revision ids and paths.** Ids are 12 hex characters with a type prefix (`prj_`,
   `pty_`, `cnt_`, `rev_`). Local paths are
   `_cindy/<project>/<container>/<code>_<file name>`, with the hash prefix added only when
   a path would otherwise collide, to keep names short (B8).
8. **Timestamps are UTC, ISO-8601 with microseconds**, generated by the author and signed,
   so `?since=` can page the record without trusting the hub's clock.
9. **`--host` defaults to `127.0.0.1`**, which is right for the demo and the tests; a LAN
   setup must pass the machine's address.
10. **A pull with any failure exits non-zero.** It still transfers what it can; the exit
    code says "not everything converged". This is what lets a caller retry blindly.
11. **`.pytest_cache/` is added to `.gitignore`** alongside the six entries in the brief,
    because running the suite creates it and it must not pollute `git status`.
